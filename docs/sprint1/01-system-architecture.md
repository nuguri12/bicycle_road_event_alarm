# System Architecture

## 1. 아키텍처 목표

이 시스템은 별도 서버를 상시 운영하지 않고 GitHub Actions에서 주기적으로 실행되는 배치형 자동화 서비스입니다.

핵심 목표는 다음과 같습니다.

- 공공 정보를 수집합니다.
- 자전거 이용자에게 의미 있는 이벤트만 선별합니다.
- 중복을 줄이고 구조화된 이벤트로 저장합니다.
- 15초 안에 읽을 수 있는 Telegram 메시지를 생성합니다.
- 실패 원인을 추적할 수 있도록 로그를 남깁니다.

## 2. 실행 방식

MVP에서는 HTTP API 서버를 운영하지 않습니다.

기본 실행 흐름:

1. GitHub Actions가 정해진 시간에 실행됩니다.
2. 설정값과 비밀값을 환경 변수에서 읽습니다.
3. 크롤러가 승인된 출처에서 원문 이벤트 후보를 수집합니다.
4. 정규화 모듈이 이벤트 필드를 표준 형식으로 변환합니다.
5. 데이터베이스 모듈이 원문과 정규화 결과를 저장하고 중복을 확인합니다.
6. 생성 모듈이 발행 대상 이벤트를 cyclist-friendly 메시지로 요약합니다.
7. Messenger 모듈이 Telegram Channel에 메시지를 발행합니다.
8. 모든 단계의 결과가 구조화 로그로 기록됩니다.

## 3. 주요 모듈

- `scheduler`: 배치 실행 진입점과 단계 orchestration
- `config`: 환경 변수, 비밀값, 실행 설정 로딩
- `crawler`: 공공 웹페이지 수집
- `normalizer`: 이벤트 필드 추출과 표준화
- `classifier`: 자전거 이용자 영향도와 이벤트 유형 분류
- `database`: Supabase PostgreSQL 접근
- `generator`: AI 또는 fallback 기반 메시지 생성
- `messenger`: Telegram Bot API 발행
- `logging`: 구조화 로그 구성
- `tests`: 단위 테스트, fixture, mock 테스트

## 4. 아키텍처 결정

### 4.1 배치 우선

사용자 수가 10명에서 100명이고 개인화가 범위에서 제외되어 있으므로, 상시 서버보다 GitHub Actions 배치가 단순하고 비용이 낮습니다.

### 4.2 FastAPI 보류

Sprint 0에서 FastAPI는 API가 필요해질 경우에만 사용하는 기술로 정의되었습니다. MVP에서는 외부 요청을 받는 API가 필요하지 않으므로 구현하지 않습니다.

### 4.3 AI 최소 사용

AI는 요약, 영향도 설명, 애매한 중복 판단 보조에만 사용합니다. 날짜 필터링, URL 비교, 필수 필드 검증은 결정적 코드로 처리합니다.

### 4.4 모듈 간 단방향 흐름

데이터는 수집에서 발행까지 한 방향으로 흐릅니다. 각 모듈은 다음 단계에 필요한 명시적 데이터 객체만 반환합니다.
