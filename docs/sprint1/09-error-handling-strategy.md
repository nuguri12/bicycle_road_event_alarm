# Error Handling Strategy

## 1. 오류 처리 목표

오류가 발생해도 가능한 범위까지 처리하고, 다음 실행에서 복구할 수 있도록 상태와 로그를 남깁니다.

## 2. 오류 분류

### 2.1 설정 오류

예:

- 필수 환경 변수 누락
- 잘못된 Telegram Channel ID
- 데이터베이스 연결 문자열 누락

처리:

- 실행 초기에 실패합니다.
- 비밀값을 제외한 설정 키 이름만 로그에 남깁니다.

### 2.2 네트워크 오류

예:

- 공공 페이지 timeout
- Telegram API 일시 실패
- OpenAI API timeout

처리:

- 제한된 횟수로 재시도합니다.
- 재시도 후 실패하면 해당 단계의 실패를 기록합니다.
- 가능한 경우 fallback 흐름으로 전환합니다.

### 2.3 HTML 구조 변경

예:

- CSS selector가 더 이상 일치하지 않음
- 필수 필드를 찾을 수 없음

처리:

- 해당 출처의 실패로 기록합니다.
- 다른 출처 처리는 계속합니다.
- 샘플 HTML fixture 업데이트가 필요한 항목으로 표시합니다.

### 2.4 데이터 검증 오류

예:

- 날짜 파싱 실패
- 장소 누락
- 원문 URL 누락

처리:

- 발행 대상에서 제외합니다.
- 원문과 오류 이유를 저장하거나 로그에 남깁니다.

### 2.5 AI 생성 오류

예:

- OpenAI API 실패
- 응답 형식 불일치
- 요약 결과가 비어 있음

처리:

- 결정적 fallback 메시지를 생성합니다.
- fallback도 실패하면 Telegram 발행을 중단하고 오류를 기록합니다.

### 2.6 Telegram 발행 오류

예:

- Bot 권한 없음
- Channel ID 오류
- Telegram API 장애

처리:

- 재시도합니다.
- 최종 실패 시 발행 실패 상태를 기록합니다.
- 동일 메시지를 다음 실행에서 중복 발행하지 않도록 발행 시도 이력을 남깁니다.

## 3. 트랜잭션 전략

- 원문 저장과 정규화 결과 저장은 Sprint 2에서 트랜잭션 경계를 확정합니다.
- Telegram 발행 성공 기록은 메시지 발행 성공 후 저장합니다.
- 발행 전 저장된 이벤트는 다음 실행에서 재사용할 수 있어야 합니다.

## 4. 구조화 로그 필드

공통 로그 필드:

- run_id
- step
- source_name
- source_url
- event_id
- severity
- error_type
- message

비밀값은 어떤 로그에도 포함하지 않습니다.

## 5. 사용자 입력 필요 항목

- `[사용자 입력 필요]` 크롤러 출처별 재시도 횟수
- `[사용자 입력 필요]` OpenAI API 실패 시 Telegram fallback 발행 승인 여부
- `[사용자 입력 필요]` Telegram 최종 발행 실패 알림 방식
