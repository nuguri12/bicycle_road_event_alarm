# Migration Strategy

## 1. 마이그레이션 도구

데이터베이스 마이그레이션은 Alembic으로 관리합니다.

선택 이유:

- SQLAlchemy 모델과 함께 사용할 수 있습니다.
- 스키마 변경 이력을 코드 리뷰할 수 있습니다.
- GitHub Actions에서 마이그레이션 적용 여부를 검증할 수 있습니다.

## 2. 마이그레이션 원칙

- Sprint 2 승인 전에는 마이그레이션 파일을 만들지 않습니다.
- 모든 스키마 변경은 Alembic revision으로 기록합니다.
- 수동 SQL 변경은 운영 긴급 상황을 제외하고 금지합니다.
- 변경 전 rollback 가능성을 검토합니다.
- 비파괴 변경을 우선합니다.

## 3. 초기 마이그레이션 범위

Sprint 2 승인 후 첫 마이그레이션은 다음 테이블만 생성합니다.

- `run_logs`
- `raw_events`
- `normalized_events`
- `publish_attempts`

초기 마이그레이션에는 사용자 계정, 관리자, 분석, 결제 관련 테이블을 포함하지 않습니다.

## 4. 변경 절차

1. 문서에서 스키마 변경 필요성을 확인합니다.
2. SQLAlchemy 모델을 수정합니다.
3. Alembic revision을 생성합니다.
4. 생성된 migration을 사람이 검토합니다.
5. 로컬 또는 테스트 데이터베이스에서 upgrade를 실행합니다.
6. downgrade 가능 여부를 확인합니다.
7. GitHub Actions에서 migration 검증을 실행합니다.

## 5. 운영 적용 정책

- MVP에서는 배포 전에 수동으로 마이그레이션 적용 결과를 확인합니다.
- 자동 migration 적용은 운영 안정성이 확인된 뒤 검토합니다.
- Supabase production 데이터베이스에 적용하기 전 테스트 프로젝트에서 먼저 검증합니다.

## 6. 사용자 입력 필요 항목

- `[사용자 입력 필요]` Supabase 테스트 프로젝트를 별도로 둘지 여부
- `[사용자 입력 필요]` 운영 DB 마이그레이션을 수동 승인으로 진행할지 여부
- `[사용자 입력 필요]` downgrade 스크립트 필수 여부
