# Non-functional Requirements

## 1. 신뢰성

- 스케줄 실행 실패가 다음 실행 전체를 막지 않아야 합니다.
- 외부 웹페이지 장애, API 장애, 네트워크 오류가 발생해도 가능한 단계까지 처리하고 실패 내역을 남깁니다.
- 동일 실행을 재시도해도 중복 알림이 발행되지 않도록 설계합니다.

## 2. 유지보수성

- 모듈은 단일 책임을 갖습니다.
- 크롤러, 정규화, AI 생성, 메시지 발행, 데이터베이스 접근은 분리합니다.
- 구현 전 각 Sprint 문서와 코드 변경이 추적 가능해야 합니다.
- 기능별 코드 블록에는 한글 주석을 사용해 의도를 설명합니다.

## 3. 비용 효율성

- 무료 또는 저비용 운영을 우선합니다.
- AI 호출은 추론이 필요한 경우로 제한합니다.
- 같은 원문을 반복 요약하지 않도록 캐시 또는 저장된 결과를 활용합니다.
- 예상 사용자 수 10명에서 100명 기준으로 과도한 인프라를 도입하지 않습니다.

## 4. 보안

- Telegram Bot Token, Supabase Key, OpenAI API Key는 코드에 저장하지 않습니다.
- GitHub Actions Secrets 또는 로컬 `.env`를 사용합니다.
- 로그에 API Key, 토큰, 전체 데이터베이스 연결 문자열을 기록하지 않습니다.

## 5. 성능

- 전체 실행은 GitHub Actions 기본 제한 시간 안에 완료되어야 합니다.
- MVP 기준 목표 실행 시간은 10분 이내입니다.
- 느리거나 실패한 출처 하나가 전체 파이프라인을 장시간 막지 않도록 타임아웃을 둡니다.

## 6. 관측 가능성

- 단계별 처리 건수, 실패 건수, 중복 제거 건수, 메시지 발행 결과를 로그로 남깁니다.
- 장애 분석을 위해 실행 ID를 사용합니다.
- 주요 오류는 원인 파악이 가능한 수준의 컨텍스트를 포함합니다.

## 7. 데이터 품질

- 이벤트 날짜, 장소, 원문 URL은 필수 데이터로 취급합니다.
- 필수 데이터가 부족한 이벤트는 발행 대상에서 제외하거나 검토 필요 상태로 저장합니다.
- 날짜가 지난 이벤트는 발행하지 않습니다.

## 8. 사용자 입력 필요 항목

- `[사용자 입력 필요]` 허용 가능한 월간 OpenAI API 비용 상한
- `[사용자 입력 필요]` GitHub Actions 실행 실패 알림을 받을 방식
- `[사용자 입력 필요]` 데이터 보관 기간에 대한 선호
- `[사용자 입력 필요]` 메시지에 원문 링크를 항상 포함할지 여부

## 9. 검증 기준

- 비밀값이 저장소에 포함되지 않아야 합니다.
- 실패 상황이 로그로 추적 가능해야 합니다.
- AI 호출 횟수가 이벤트 수에 비례해 불필요하게 증가하지 않아야 합니다.
