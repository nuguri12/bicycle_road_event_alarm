# Crawler Strategy

## 1. 기본 전략

크롤러는 작고 독립적인 출처별 어댑터로 구현합니다.

기본 흐름:

1. 출처 목록 페이지를 요청합니다.
2. 이번 주말 또는 설정된 기간과 관련 있어 보이는 상세 URL을 추출합니다.
3. 상세 페이지를 요청합니다.
4. 원문 제목, 날짜 문자열, 장소 문자열, 본문 요약, 원문 URL을 추출합니다.
5. `Raw Event Candidate` 목록을 반환합니다.

## 2. 기간 필터링

크롤러 단계에서는 지나치게 강한 필터링을 하지 않습니다.

원칙:

- 목록 페이지에서 명백히 오래된 게시글은 제외합니다.
- 날짜가 애매한 게시글은 정규화 단계로 넘깁니다.
- 기본 수집 범위는 "오늘부터 다음 14일"을 후보로 둡니다.

이유:

- 공지 제목만으로 주말 영향 여부를 판단하기 어렵습니다.
- 과도한 초기 필터링은 누락 위험을 키웁니다.

## 3. 키워드 필터링

목록 또는 검색이 필요한 출처에는 다음 키워드를 사용합니다.

기본 키워드:

- 자전거
- 도로통제
- 교통통제
- 마라톤
- 달리기
- 걷기
- 축제
- 행사
- 한강
- 공원
- 하천

주의:

- 키워드는 후보 축소용이며 최종 발행 판단이 아닙니다.
- 출처가 자체 검색을 지원하지 않으면 목록을 가져온 뒤 제목 기준으로만 적용합니다.

## 4. HTTP 요청 정책

- 기본 timeout은 10초로 둡니다.
- User-Agent는 프로젝트 식별이 가능한 일반적인 문자열을 사용합니다.
- 같은 출처에 과도하게 빠른 반복 요청을 하지 않습니다.
- MVP에서는 병렬 크롤링을 기본으로 하지 않습니다.

## 5. HTML 파싱 정책

- 목록 selector와 상세 selector를 분리합니다.
- 필수 selector가 실패하면 해당 출처 실패로 기록합니다.
- 본문 전체 저장보다 필요한 텍스트 추출을 우선합니다.
- HTML 구조 변경에 대비해 fixture 기반 테스트를 작성합니다.

## 6. 사용자 입력 필요 항목

- `[사용자 입력 필요]` 기본 수집 범위 14일 승인 여부
- `[사용자 입력 필요]` 키워드 목록 추가 또는 제외 항목
- `[사용자 입력 필요]` 출처별 요청 간 최소 대기 시간
- `[사용자 입력 필요]` 병렬 크롤링을 MVP에서 금지할지 여부
