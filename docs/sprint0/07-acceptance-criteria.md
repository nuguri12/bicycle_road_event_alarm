# Acceptance Criteria

## 1. Sprint 0 승인 기준

- Functional Requirements Specification이 MVP 범위와 제외 범위를 명확히 설명합니다.
- Non-functional Requirements가 신뢰성, 보안, 비용, 관측 가능성 기준을 포함합니다.
- Project Roadmap이 Sprint 0부터 Sprint 9까지 순서를 유지합니다.
- Risk Analysis가 주요 실패 모드와 완화 전략을 포함합니다.
- Technology Selection Report가 선택 기술과 보류 기술을 구분합니다.
- Development Milestones가 각 단계의 완료 조건과 검증 방법을 포함합니다.
- 이 문서가 다음 Sprint 진입 기준을 명확히 정의합니다.

## 2. Sprint 1 진입 기준

- Sprint 0 문서가 사용자에게 승인됩니다.
- `[사용자 입력 필요]` 항목 중 Sprint 1 설계에 필요한 항목이 확정됩니다.
- 구현 금지 상태가 유지됩니다.

## 3. MVP 최종 승인 기준

- 정해진 스케줄에 따라 자동 실행됩니다.
- 하나 이상의 승인된 공공 출처에서 이벤트를 수집합니다.
- 이벤트를 정규화하고 데이터베이스에 저장합니다.
- 중복 이벤트를 제거하거나 발행 대상에서 제외합니다.
- 자전거 이용자 관점의 짧은 메시지를 생성합니다.
- Telegram Channel에 메시지를 발행합니다.
- 실패 상황을 구조화 로그로 남깁니다.
- 비밀값이 저장소에 포함되지 않습니다.

## 4. 메시지 승인 기준

- 메시지는 주말 라이딩 전 사용자가 15초 이내에 읽을 수 있어야 합니다.
- 피해야 할 지역 또는 구간이 명확해야 합니다.
- 시간대 또는 날짜가 포함되어야 합니다.
- 이벤트 이유가 간단히 설명되어야 합니다.
- 가능한 경우 원문 링크를 포함해야 합니다.
- 불확실한 정보는 단정하지 않아야 합니다.

## 5. 품질 승인 기준

- 구현 후 관련 Pytest가 통과해야 합니다.
- Ruff, Black, Mypy 검사를 통과해야 합니다.
- 테스트가 불가능한 외부 API는 mock 또는 fixture로 검증해야 합니다.
- 기능별 코드 구간은 한글 주석으로 의도를 설명해야 합니다.
- 불필요한 AI 호출이 없어야 합니다.
- MVP 제외 범위 기능이 구현되지 않아야 합니다.

## 6. 운영 승인 기준

- GitHub Actions Secrets 목록이 문서화되어야 합니다.
- 수동 재실행 방법이 문서화되어야 합니다.
- Telegram 발행 실패 시 확인 방법이 문서화되어야 합니다.
- 데이터베이스 백업 또는 복구 방침이 문서화되어야 합니다.

## 7. 사용자 입력 필요 항목

- `[사용자 입력 필요]` Sprint 0 승인 여부
- `[사용자 입력 필요]` Sprint 1로 진행할지 여부
- `[사용자 입력 필요]` MVP 최종 메시지 예시 선호안
- `[사용자 입력 필요]` 품질 도구 중 반드시 적용할 항목과 보류 가능한 항목
